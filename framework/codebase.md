## 1. What This Framework Is

A lightweight, multi-tenant PHP MVC framework. No Laravel, no Symfony, no Composer dependencies. Everything is hand-rolled and explicit. The design philosophy is: readable over clever, explicit over magic.

**Key characteristics:**
- Two independent, single-path PSR-4 namespace roots: `Frank\` resolves to `framework/` (framework-owned code), `App\` resolves to `app/` (application-owned code). No searching or fallback between them — a class's namespace alone determines where it's found. See §2.
- Multi-tenancy is a first-class citizen — every authenticated route is tenant-scoped
- Middleware pipeline handles auth, tenant resolution, and JSON parsing before the controller is touched
- Models handle DB access only — no business logic, no Clock calls
- Business logic lives exclusively in Services — including all timestamp generation via Clock
- Views use output buffering into a layout file — no templating engine
- A minimal explicit DI container wires services and controllers — framework bindings in `framework/bootstrap.php`, application bindings in `app/bootstrap.php`

### Foundational Principle: Reuse Before You Add

Code reusability is fundamental to building maintainable software, and FrankPHP treats it as a core rule for framework code and for every application built on it. It applies equally to Controllers, Services, Models, Middleware and every other class. A codebase full of near-duplicate and single-use methods turns into rambling code that nobody can safely change.

**Write for reuse.** Reusability is a priority from the moment code is written, not something cleaned up later.

- **Reuse an existing method before adding a new one**, even if the call is shaped slightly differently: a different argument, a loop around the call, or a filter on the result.
- **Write every new method as a general operation** that other callers can use, not as a helper for the one place that needs it today. No single-use methods, in any layer.
- **Every proposed code change states which existing methods it reuses.**
- **Every new method is justified:** the proposal says why no existing method can do the job.

**Remove redundant code immediately.**

- **Methods left unused when a design changes are removed** in the same change. Code from a discarded approach is not kept "in case".
- **A method that duplicates an existing one is removed** and its callers are pointed to the existing method.

**Example.** A service needs to remove loaded dates one at a time. Two existing Model methods already do the job, so no new method is added at any layer:

```php
// Reuses Ranking::findFetchDatesFrom() and Ranking::deleteBefore()
$dates = $this->rankingModel->findFetchDatesFrom('1000-01-01'); // every loaded date
foreach ($dates as $date) {
    $this->rankingModel->deleteBefore($date); // one date per statement
}
```

## 2. Directory Structure

**v2.0.0 architecture: two sibling folders, `framework/` and `app/`, at the project root.** `framework/` is replaced wholesale on every framework update; `app/` is never touched by an update, once a developer has customized it. This physical split is the mechanism behind the framework/application ownership boundary described throughout this document — see §15.2.

```
/
├── framework/               # Replaced wholesale on update. Never contains application code.
└── app/                     # Never touched by a framework update. The developer's own project.
```

## 3. Request Lifecycle

```
app/public/index.php (entry point)
  └── sets APP_BASE_DIR constant (two levels up from public/ — the project root, containing framework/ and app/)
  └── requires framework/bootstrap.php → gets $router
        └── namespace-partitioned autoloader registered — Frank\ → framework/, App\ → app/
        └── layout guard — throws a clear RuntimeException if APP_BASE_DIR/app/bootstrap.php is missing
        └── Env::load() reads app/.env → populates $_ENV (must run before config.php)
        └── app/Config/config.php required → reads from $_ENV
        └── Database::connect() called with config values
        └── APP_VIEWS_DIR and FRANK_VERSION constants defined
        └── Container created → framework services registered as singletons
        └── Router created → receives Container
        └── framework routes registered (sign-in / verify / terms / logout, tenant/account settings)
        └── hard-requires app/bootstrap.php as its final step, passing $container/$router/$config already in scope
              └── app/bootstrap.php registers application routes and container bindings, returns $router
  └── $router->dispatch(new Request())
        └── matches route pattern
        └── builds middleware pipeline (outermost first, innermost last)
        └── each middleware calls $next($request) to continue
        └── Router checks Container for controller binding before falling back to new $controller()
        └── controller method receives (Request $request, array $params)
        └── returns Response::view() / Response::json() / Response::redirect()
```

**`APP_BASE_DIR` contract (since v2.0.0).** `APP_BASE_DIR` is the **project root** — the folder that contains both `framework/` and `app/` — never the `app/` folder itself. `app/public/index.php` must set it with exactly:

```php
define('APP_BASE_DIR', dirname(__DIR__, 2));
$router = require_once APP_BASE_DIR . '/framework/bootstrap.php';
```

Application code refers to its own files as `APP_BASE_DIR . '/app/...'` (or `APP_VIEWS_DIR` for views). The pre-2.0 form `dirname(__DIR__, 1)` is wrong. Since v2.1.1 `framework/bootstrap.php` detects it before loading `.env` and throws a `RuntimeException` that quotes the two correct lines. `tests/boot_layout_test.php` covers both layouts. Run it before every release.

A missing `app/bootstrap.php` is a fatal boot error by design — there is no shared file left for an application route to accidentally land in the wrong half of.

**Middleware execution order for a standard tenant route `[$tm, $auth]`:**
1. `TenantMiddleware` — resolves `{tenant_id}` from route params, loads tenant row, sets `$request->tenant`
2. `AuthMiddleware` — starts the session (`Session::start()`), checks `$_SESSION['user_id']`, loads user row, validates user belongs to tenant, sets `$request->user`
3. Controller method executes

**If any middleware fails:** it calls `Response::redirect()` or `http_response_code()` and returns without calling `$next` — the pipeline stops.

## 4. Routing

Framework routes are defined in `framework/bootstrap.php`; application routes are defined in `app/bootstrap.php`. Both use the same `$router` — the router is returned and dispatched from `app/public/index.php`. Use `$router->override(...)` instead of `$router->add(...)` to deliberately replace a framework-registered route from `app/bootstrap.php`; `add()` throws on a duplicate (method, pattern) pair.

```php
$router->add(METHOD, PATTERN, HANDLER, [MIDDLEWARE]);
```

**Handler formats:**
```php
'ControllerName@method'                    // shorthand — resolves to App\Controllers\ControllerName. Used for application routes.
'Frank\\Controllers\\Full\\Path@method'    // fully qualified — used for every framework route
'App\\Controllers\\Full\\Path@method'      // fully qualified — equivalent to the shorthand above
```

The bare shorthand always expands to `App\Controllers\`, never `Frank\Controllers\` — framework routes must use the fully-qualified `Frank\Controllers\...` form. This is intentional, not an oversight: it means a bare handler string in application code always means "my own controller."

**Route parameter syntax:** `{param_name}` — captured into `$request->routeParams['param_name']`

**Middleware shorthands** (defined as variables in `framework/bootstrap.php`, in scope for `app/bootstrap.php` too):
```php
$tm      = 'Frank\\Middleware\\TenantMiddleware';
$auth    = 'Frank\\Middleware\\AuthMiddleware';
$apiAuth = 'Frank\\Middleware\\ApiAuthMiddleware';
$json    = 'Frank\\Middleware\\JsonBodyParserMiddleware';
```

Application-defined middleware follows the same bare-shorthand-resolves-to-`App\Middleware\` pattern as controller handlers.

**Standard middleware combinations:**
- Public page: `[]`
- Public POST (sign-in code request / verify / terms): `[$json]`
- Authenticated tenant page: `[$tm, $auth]`
- Authenticated tenant POST: `[$tm, $auth, $json]`
- API endpoint: `[$tm, $apiAuth, $json]`

**Important:** `$json` populates `$request->bodyParams`. Without it, POST body is only available via `$_POST`.

## 5. Controllers

Extend `BaseController`. Receive `(Request $request, array $params)`. This is an application controller — it lives under `App\Controllers` in `app/Controllers/`, but `BaseController`/`Request`/`Response` are always imported from `Frank\Core`, never `App\Core` — those classes are framework-owned regardless of which side the concrete controller lives on.

```php
namespace App\Controllers;

use Frank\Core\BaseController;
use Frank\Core\Request;
use Frank\Core\Response;

class ExampleController extends BaseController
{
    public function index(Request $request, array $params): mixed
    {
        $tenant = $request->tenant; // set by TenantMiddleware
        $user   = $request->user;   // set by AuthMiddleware

        return $this->view('section/view-name', [
            'title'  => 'Page Title',
            'tenant' => $tenant,
            'user'   => $user,
        ]);
    }
}
```

A framework controller follows the identical pattern one namespace over: `namespace Frank\Controllers;`, same `use Frank\Core\...` imports.

**Controllers with service dependencies** receive them via constructor injection (wired in `framework/bootstrap.php` for framework controllers, `app/bootstrap.php` for application controllers). See Section 8.2.

```php
class AuthController extends BaseController
{
    public function __construct(
        private LoginCodeService    $loginCodeService,
        private UserService         $userService,
        private InviteService       $inviteService,
        private GoogleSignInService $googleSignInService,
        private array               $config = []
    ) {}
}
```

**`$this->view($name, $params)`** resolves to `Views/$name.php`, extracts `$params` into scope, and requires the file. The view file is responsible for buffering its own content and requiring a layout.

**Reading request data:**
```php
$request->bodyParams           // parsed JSON or $_POST (requires $json middleware)
$request->post                 // raw $_POST
$request->get                  // $_GET
$request->routeParams          // URL segment params e.g. ['tenant_id' => '1']
$request->input('key', $default) // checks bodyParams → post → get in order
$request->header('Name')       // request header
$request->tenant               // tenant array (set by TenantMiddleware)
$request->user                 // user array (set by AuthMiddleware)
```

## 6. Views and Layouts

Views use PHP output buffering. The pattern is consistent across all views:

```php
<?php
$title = 'Page Title';
ob_start();
?>
<!-- HTML content here — $tenant, $user, and any passed params are in scope -->
<?php
$content = ob_get_clean();
require APP_VIEWS_DIR . '/layouts/app-main.php'; // or authViews.php
?>
```

`APP_VIEWS_DIR` is a constant defined once in `framework/bootstrap.php` (see §2) — always use it, never a relative `__DIR__` path, so a view file works the same regardless of which subfolder it lives in.

**Layouts:**
- `app-main.php` — full authenticated shell. Renders `$content` inside `.page-content-area`. Includes header and nav partials. Expects `$title`, `$tenant`, `$user` in scope.
- `authViews.php` — minimal unauthenticated shell. Renders `$content` only. Used for the sign-in screens (login, verify, terms).

**Variables available in views** (via `extract()` in `Response::view()`): everything passed in the params array to `$this->view()`.

**View responsibility boundary.** Views output variables; they do not compute them. This is a hard framework rule that applies to every application built on FrankPHP:

- A view **may** branch on a boolean flag that has already been resolved by the Service or Controller (`$canEdit`, `$hasPriorData`, `$canFinish`).
- A view **must not** derive or compute that flag itself.
- A view **may** echo a scalar value (`$prefillReps`, `$statusLabel`).
- A view **must not** select that scalar by choosing between two data sources (`$prior['actual_reps'] ?? $current['target_reps']`).
- Any `??`, ternary, or conditional that decides *which data wins* is business logic. It belongs in the Service. The Service delivers a complete, flat set of named, ready-to-render values; the view echoes them.

A view that resolves priority between data sources must be refactored — this is not an acceptable deviation and must not be recorded in MYAPP.md as one. The correct fix is always to push the resolution into the Service and pass the result as a named scalar.

## 7. Models

### The Model SoC Contract

**Models handle DB access only.** This is a hard framework rule introduced in v1.3.2 and applies to every model in the framework and every application model built on top of it.

- A model **must not** call `Frank\Core\Clock`.
- A model **must not** make business-logic decisions (rate-limit comparisons, hash verification, name derivation, field priority resolution).
- All timestamp values (`now`, `expiresAt`, `cutoff`, `threshold`) are computed by the calling Service via Clock and passed to model methods as plain `string` parameters.
- Model method signatures make this explicit — any method needing a timestamp accepts it as a named `string` parameter.

**The correct pattern:**
```php
// In a Service:
$now = Clock::nowUtcString();
$this->userModel->markLoginCodeUsed($codeId, $now); // model receives string, never calls Clock

// WRONG — model must not do this:
public function markLoginCodeUsed(int $id): bool {
    // Clock::nowUtcString() here is a SoC violation
}
```

### BaseModel

All application models that map to a single DB table should extend `BaseModel`. `BaseModel` itself is framework-owned — the import is always `Frank\Core\BaseModel`, even though the concrete model class lives under `App\Models`.

```php
namespace App\Models;
use Frank\Core\BaseModel;

class Thing extends BaseModel
{
    protected string $table = 'things'; // optional — defaults to lowercase classname + 's'

    // Declare all columns as typed public properties
    public ?int    $id         = null;
    public int     $tenant_id;
    public string  $name;
    public ?string $created_at = null;
}
```

**Key methods:**

| Method | Description |
|--------|-------------|
| `fill(array $data)` | Hydrates properties from array, casting to declared PHP types |
| `save()` | INSERT ... ON DUPLICATE KEY UPDATE — works for both create and update |
| `delete()` | DELETE by primary key, AND tenant_id if property exists |
| `find(int $id, int $tenantId)` | Returns hydrated object or null — tenant-scoped |
| `all(int $tenantId)` | Returns array of hydrated objects — tenant-scoped |
| `where(int $tenantId, string $col, mixed $val, string $op)` | Returns array of hydrated objects |

**Type casting in `fill()`:**
- `int`, `float`, `bool`, `string` — cast directly
- `float` — strips `$` and `,` (currency cleaning)
- `bool` — uses `filter_var` with `FILTER_VALIDATE_BOOLEAN`
- `DateTimeImmutable` / `DateTime` — constructed from value string
- `array` — parsed from JSON string or comma-separated string
- Nullable properties receiving `""`, `null`, or `"-1"` are set to `null`

**`save()` excludes** `id`, `created_at`, `tenant_id` from the UPDATE clause (they are included in the INSERT). Every other property, including `updated_at`, is written back as the object holds it: a property the Service did not change is written back exactly as `find()` fetched it.

**`updated_at` is the Service's responsibility (v3.0.0).** `BaseModel` never sets `updated_at`. When a Service changes a record and that change should count as an update, the Service sets `updated_at` with `Clock::nowUtcString()` before calling `save()`. If the Service does not set it, `save()` writes back the fetched value and `updated_at` does not change.

```php
// In a Service:
$user = User::find($userId, $tenantId);
$user->name       = $newName;
$user->updated_at = Clock::nowUtcString(); // the Service manages updated_at, via Clock
$user->save();
```

### Tenant Model

`Tenant` does **not** extend `BaseModel`. It is a standalone class with its own PDO instance.

Key methods: `findById(int $id)`, `findAll()`, `slugExists(string $slug)`, `insertTenant(name, slug, companyEmail, createdAt)` *(v2.1.0)*, `saveSettings(int $tenantId, array $data, string $updatedAt)`.

`saveSettings()` has an internal allowlist of writable columns — only those columns can be updated via settings forms. The `$updatedAt` UTC string is computed by the calling Service and passed in — `Tenant` never calls Clock.

## 8. Services and ServiceResult

Business logic that is more than a single DB call lives in a Service class. Framework-owned services live in `framework/Services/` under `Frank\Services\`; application-owned services live in `app/Services/` under `App\Services\`. Both follow the identical pattern below.

Services return a `ServiceResult` object.

**Services own all Clock calls.** Timestamp strings produced by Clock are passed down to model methods as plain parameters. Models never call Clock.

**Services own `updated_at`.** When a Service changes a record, it is the Service's responsibility to set `updated_at` using `Clock::nowUtcString()` before `save()`. Neither `BaseModel` nor any model sets it (see BaseModel, `save()`).

**ServiceResult interface:**
```php
$result->success          // bool
$result->message          // string — error or info message
$result->data             // array — full result payload
$result->get('key')       // retrieve a named value from the result payload
$result->get('key', $default)
$result->isValidationError()  // bool
$result->isRateLimitError()   // bool
$result->isSystemError()      // bool
```

**Controller pattern — delegate, don't decide:**
```php
// Services are injected — never constructed inside controller methods
$result = $this->myService->doSomething($input);

if ($result->success) {
    Response::redirect('/somewhere');
}

return $this->view('some/view', ['error' => $result->message]);
```

### 8.1 EmailService

`Frank\Services\Email\EmailService` is the single SMTP gateway for the entire application. It is always constructed via the DI container using `EmailService::fromConfig($config['mail'])` — credentials come from `.env`, never from call sites.

**Constructor:** Do not call directly. Use `fromConfig()` or the container.

**Framework-owned send methods** — these exist because framework-owned Services call them directly (see §15.2):

| Method | Purpose |
|--------|---------|
| `sendLoginCode(email, code, expiryMinutes)` | The emailed 6-digit sign-in code (v3.0.0). One email for both sign-in and sign-up; code only, no link |
| `sendInvite(email, inviteUrl, expiryDays)` | The invite email (v3.0.0). Called by `InviteService`, which builds the link `/invite/{tenant_id}/{token}`. One email for both kinds of invite (§16.11) |
| `sendPlatformOwnerSignupAlert(triggeringEmail, event)` | Alerts the platform owner (`MAIL_SITE_ADMIN`) twice, as in v2: when an address with no account requests a code, and when the account is created |

Each renders a default template shipped in `Services/Email/Templates/`. The template *class* — not this method — is what's overridable per-application, via `config('mail.templates')`, without editing this file. See §16.8, "Overriding Framework Email Templates." All three build their `EmailMessage` through one private helper, `sendTemplated(to, subject, htmlBody, textBody)`, which fills in the SMTP credentials, sender and reply-to from config (v3.0.0).

**`EmailAddress`** *(v3.0.0)* — `Frank\Services\Email\EmailAddress`, the one place that defines email rules: `EmailAddress::normalise(email)` (trim, lower-case) and `EmailAddress::isValid(email)` (valid format, at most 255 characters — `users.email` size). Static, `final`. Used by `LoginCodeService`, `InviteService`, `TenantNameGenerator` and `EmailMessage::isValid()`. `users.email` is unique across the platform, so any code that compares or stores an address must go through it, never inline. App code may call it too.

**Adding a new email type for application use:** do not add `send*()` methods to this framework-owned class. Write an application-owned service (e.g. `App\Services\NotificationService`) that constructs its own `EmailMessage` and calls the injected `EmailService::send()` directly — the same pattern as any other application-owned service.

**`EmailMessage`** — value object: `to`, `toName`, `subject`, `htmlBody`, `textBody`, `from`, `fromName`, `replyTo`, `credentialsUserName`, `credentialsUserSecret`. `from` and `fromName` are required constructor arguments — the framework does not default them to any brand identity.

**`EmailResult`** — result object: `success` (bool), `message`, `emailId`, `error`. Static constructors: `EmailResult::success()`, `EmailResult::failure($error)`.

### 8.2 Dependency Injection Container

`Frank\Core\Container` is a minimal explicit DI container. No reflection, no autowiring. Every binding is a PHP closure — framework bindings registered in `framework/bootstrap.php`, application bindings registered in `app/bootstrap.php`.

**API:**

| Method | Behaviour |
|--------|-----------|
| `singleton(id, callable)` | Factory is called once; result is cached and reused on every `make()`. Throws if `id` is already bound. |
| `bind(id, callable)` | Factory is called fresh on every `make()` — for per-request objects (rare). Throws if `id` is already bound. |
| `override(id, callable, shared = true)` | Deliberately replaces an existing binding — the only way to rebind an `id` that's already registered |
| `make(id)` | Resolve by id. Throws `RuntimeException` if no binding registered |
| `has(id)` | Returns bool — used by Router before falling back to `new $controller()` |

**The factory callable always receives the container as its argument**, so services that depend on other services call `$c->make(OtherService::class)` rather than nesting construction.

**What is registered in the container** (framework bindings, registered in `framework/bootstrap.php` — application bindings are registered separately in `app/bootstrap.php`, see the pattern below):

| Id (class string) | Type | Why |
|---|---|---|
| `EmailService::class` | singleton | Config-driven SMTP credentials; shared across all services |
| `SignupTenantResolver::class` | singleton | New-account tenant-placement policy — default `CreateTenantForSignup`. Replace with `override()` (§16.9). v2.1.0 |
| `AccountService::class` | singleton | The one place a new account is created (sign-up and invites). Depends on EmailService (§16.9, §16.11). v3.0.0 |
| `LoginCodeService::class` | singleton | Depends on User model + EmailService + SignupTenantResolver + AccountService + `$config['signup']` (§11, §16.9). v3.0.0 |
| `UserService::class` | singleton | Framework user business logic — recordLogin, saveSettings |
| `TenantService::class` | singleton | Framework tenant business logic — saveSettings allowlist and null-coercion |
| `InviteService::class` | singleton | Depends on EmailService + AccountService + TenantService + User model + `$config['signup']` (§16.11). v3.0.0 |
| `GoogleSignInService::class` | bind | Keys from `$config['oauth']['google']` (optional); return address `Url::baseUrl() . '/login/google/callback'` (§11). v3.0.0 |
| `AuthController::class` | bind | Needs LoginCodeService + UserService + InviteService + GoogleSignInService injected, plus `$config` (its `oauth` keys decide which sign-in buttons are enabled) |

Controllers are registered with `bind()` (not `singleton()`) because a fresh controller instance per request is the correct behaviour.

**What is NOT in the container:**
- Models — lightweight, `new Model()` in service constructors is fine
- Middleware — constructed by the Router pipeline; no injected dependencies
- `Request` / `Response` — per-request value objects
- `Clock` — stateless static core utility loaded by PSR-4, no binding required
- Controllers with no constructor dependencies — Router falls back to `new $controller()`

**Router integration:** `Router::__construct(?Container $container)`. On handler resolution, the Router calls `$container->has($controllerClass)` first. If a binding exists, it uses `$container->make()`. Otherwise it uses `new $controller()`. This means controllers without constructor dependencies require zero changes.

**Registering a new service (the full pattern):**

```php
// In app/bootstrap.php — $container, $router, $config are already in scope

// 1. Register the service. BillingService is a new application service, so it's
//    App\Services\... — but it depends on the framework's EmailService and Database,
//    which are always Frank\..., regardless of which side is doing the depending.
$container->singleton(\App\Services\BillingService::class, function ($c) use ($config) {
    return new \App\Services\BillingService(
        $c->make(\Frank\Services\Email\EmailService::class),
        \Frank\Core\Database::getPdo(),
        $config['billing']         // any config section the service needs
    );
});

// 2. Register the controller that depends on it (only if it has constructor dependencies)
$container->bind(\App\Controllers\BillingController::class, function ($c) {
    return new \App\Controllers\BillingController(
        $c->make(\App\Services\BillingService::class)
    );
});
```

**Adding a new email type for application use** (the companion pattern to the above) — do not add a `send*()` method to the framework's `EmailService` (see §8.1). Write an application-owned service instead:
```php
// app/Services/NotificationService.php
namespace App\Services;

use Frank\Services\Email\EmailService;
use Frank\Services\Email\EmailMessage;
use Frank\Services\Email\EmailResult;

class NotificationService
{
    public function __construct(private EmailService $emailService) {}

    public function sendInvoice(string $email, string $name, string $invoiceUrl): EmailResult
    {
        $htmlBody = InvoiceEmailTemplate::buildHtml($name, $invoiceUrl);

        return $this->emailService->send(new EmailMessage(
            credentialsUserName:   /* from injected config, not hardcoded */,
            credentialsUserSecret: /* from injected config, not hardcoded */,
            to:       $email,
            subject:  'Your Invoice',
            htmlBody: $htmlBody,
            from:     /* from injected config */,
            fromName: /* from injected config */,
        ));
    }
}
```

## 9. Database

`Database::connect(array $config)` creates the PDO singleton. Called once in `framework/bootstrap.php`. The config array is built from `$_ENV` values populated by `Env::load()` — credentials live in `app/.env`, not in `config.php` directly.

`Database::getPdo()` returns the singleton — called by `BaseModel::__construct()` and standalone models.

**On first boot:** if the `users` table does not exist, `schema.core.sql` is executed automatically via `Database::runSchemaFileIfMissingTable()`. A fresh install starts **empty** (v3.0.0): no seeded tenant and no seeded users — the first person to verify an emailed sign-in code creates the first tenant and becomes its owner (§11).

`Database::runSchemaFileIfMissingTable(path, sentinelTable)` is a general-purpose primitive, not specific to the core schema — application code may call it a second time for its own `app/sql/schema.app.sql`, guarded by an application-chosen sentinel table. See §16.7 for the full pattern and why this exists.

`Database::transaction(callable $fn)` *(v2.1.0)* runs `$fn` in one transaction on the shared connection — commits on return, rolls back and rethrows on any `Throwable`. Every model defaults to the same `getPdo()` connection, so writes across `User` and `Tenant` inside the callable are atomic. Called from Services (e.g. `LoginCodeService` creating a tenant + owner user), never from Models.

**PDO settings:** `ERRMODE_EXCEPTION`, `FETCH_ASSOC`.

All queries use prepared statements. Multi-statement mode is enabled only during schema import, then disabled.

**Date/time storage rule:** persisted application timestamps must be generated in UTC by application code using `Frank\Core\Clock`. Do not use SQL `NOW()` / `CURRENT_TIMESTAMP` for framework-managed or application-managed timestamps unless a specific deviation is documented.

## 10. Date and Time Handling

FrankPHP v1.3.0 introduces `Frank\Core\Clock` as the framework-owned date/time utility.

The framework rule is:

> UTC at rest. Local at the edges.

This means:
- Persisted `DATETIME` values are stored as UTC unless a column explicitly documents otherwise.
- User, tenant, and application timezones are used to interpret inputs, prepare outputs, and calculate query boundaries.
- Timezone preferences are never stored into timestamp columns.
- Services prepare display-ready date/time values for views.
- Views must not perform timezone conversion, timestamp comparison, date fallback logic, or relative date labelling.

### 10.1 `Frank\Core\Clock`

`Clock` lives at:

```text
Core/Clock.php
```

Namespace:

```php
Frank\Core\Clock
```

It is loaded by the existing PSR-4 autoloader and does not require a container binding while it remains a stateless static framework utility.

`Clock` owns:
- UTC timestamp generation
- UTC offset calculation
- UTC/local conversion
- Local input parsing into UTC storage values
- UTC storage value formatting into local display values
- Timezone validation
- Timezone resolution from explicit user, tenant, and config arrays
- UTC query boundary calculation from local dates

`Clock` must not read from:
- `$_SESSION`
- `$_SERVER`
- global request state
- the database
- middleware state
- controller globals

Callers must pass explicit context.

### 10.2 Timezone Resolution

Resolved timezone order:

```text
user.timezone
→ tenant.timezone
→ config['timezone']
→ UTC
```

`Clock::resolveTimezone($user, $tenant, $config)` formalises this rule.

Supported sources:
- `users.timezone`
- `users.settings` JSON containing `timezone`
- `tenants.timezone` if present in an application/framework version
- `tenants.settings` JSON containing `timezone`
- `config['timezone']`, normally populated from `APP_TIMEZONE`
- fallback `UTC`

If a timezone value is missing, empty, or invalid, the next candidate is tried. If all candidates fail, UTC is used.

### 10.3 Storage Rules

All framework and application timestamp writes should use `Clock` **in the Service layer**:

```php
use Frank\Core\Clock;

$createdAt = Clock::nowUtcString();
$expiresAt = Clock::utcOffsetString('+1 hour');
$recentCutoff = Clock::utcOffsetString('-30 days');
```

Do not use this for persisted application timestamps:

```php
date('Y-m-d H:i:s');
time();
new DateTime('now');
```

Do not use this in SQL for framework-managed or application-managed timestamps:

```sql
NOW()
CURRENT_TIMESTAMP
```

Prefer bound UTC parameters:

```php
$cutoff = Clock::utcOffsetString('-30 days');

$stmt = $pdo->prepare('
    SELECT *
    FROM users
    WHERE tenant_id = :tenant_id
      AND last_seen_at >= :cutoff
');

$stmt->execute([
    'tenant_id' => $tenantId,
    'cutoff' => $cutoff,
]);
```

### 10.4 Input Rules

User-entered date/time values are interpreted in the resolved local timezone and converted to UTC before storage.

```php
$timezone = Clock::resolveTimezone($request->user, $request->tenant, $config);

$startsAtUtc = Clock::localInputToUtcString(
    $request->input('starts_at'),
    $timezone,
    'Y-m-d H:i'
);
```

Date-only values with no time-of-day meaning must use `DATE`, not `DATETIME`.

Examples:
- birthday → `DATE`
- local calendar-only due date → `DATE`
- event starts at an exact instant → UTC `DATETIME`
- sign-in code expiry → UTC `DATETIME`

### 10.5 Output Rules

Stored UTC values are converted to the resolved local timezone before display.

```php
$timezone = Clock::resolveTimezone($user, $tenant, $config);

$lastSeenLabel = $row['last_seen_at']
    ? Clock::formatUtcForTimezone($row['last_seen_at'], $timezone, 'j M Y, H:i')
    : 'Never seen';
```

`Clock` may perform mechanical formatting. Product-specific labels such as `Never`, `Today`, `Yesterday`, `Recently active`, `Inactive`, or `Dormant` belong in Services because they are business/display semantics.

Views receive already-prepared values such as:

```php
'lastSeenLabel' => '6 Jun 2026, 14:30'
```

Views must not call `Clock`.

### 10.6 Query Boundary Rules

Local date filters must be converted into UTC boundaries before querying.

```php
$timezone = Clock::resolveTimezone($user, $tenant, $config);

$range = Clock::utcRangeForLocalDate('2026-06-06', $timezone);

$stmt = $pdo->prepare('
    SELECT *
    FROM users
    WHERE tenant_id = :tenant_id
      AND last_seen_at BETWEEN :start_utc AND :end_utc
');

$stmt->execute([
    'tenant_id' => $tenantId,
    'start_utc' => $range['start'],
    'end_utc' => $range['end'],
]);
```

Relative filters such as "last 30 days" must also calculate UTC boundaries in PHP through `Clock`.

### 10.7 MySQL `TIMESTAMP` Migration Rule

FrankPHP prefers UTC `DATETIME` for persisted application timestamps.

Existing applications using MySQL `TIMESTAMP` columns should not blindly convert every date-like field. First classify the column:

| Meaning | Preferred type |
|---------|----------------|
| Exact instant in time | UTC `DATETIME` |
| Expiry timestamp | UTC `DATETIME` |
| Login/activity timestamp | UTC `DATETIME` |
| External provider timestamp | Normalised UTC `DATETIME`, optional raw payload separately |
| Date-only value | `DATE` |

When converting existing MySQL `TIMESTAMP` columns to `DATETIME`, run the migration session in UTC:

```sql
SET time_zone = '+00:00';

ALTER TABLE example_table
  MODIFY created_at DATETIME NOT NULL,
  MODIFY updated_at DATETIME NULL;
```

If historical values were stored in local wall-clock time by mistake, a deliberate data correction step is required before or during migration. Do not assume the historical timezone.

### 10.8 Build Rules for Date/Time Code

When building or reviewing FrankPHP code:

- Use `Frank\Core\Clock` for persisted timestamps — in Services only.
- Models must never call Clock. Timestamps arrive as string parameters.
- Use UTC `DATETIME` for exact instants.
- Use `DATE` for date-only values.
- Do not use SQL `NOW()` / `CURRENT_TIMESTAMP` for application-managed timestamps.
- Do not perform timezone conversion in Views.
- Do not calculate "today", "last 30 days", or local date ranges directly in SQL.
- Resolve timezone explicitly with `Clock::resolveTimezone($user, $tenant, $config)`.
- Pass display-ready date labels from Services to Views.
- Document any intentional deviation in `MYAPP.md` for application code, or in `CHANGELOG.md` / `CODEBASE.md` for framework code.

## 11. Authentication and Multi-tenancy

**Passwordless (v3.0.0).** There are no passwords anywhere in the framework. One screen (`/login`) signs people in and signs new people up: the person enters an email address and is emailed a 6-digit code (code only, no link). Whatever they do, the screens and messages are identical for known and unknown addresses until the code is verified.

**Session:** PHP native sessions, always started through `Frank\Core\Session::start()` — never bare `session_start()` (`app/public/index.php` and `AuthMiddleware` both use it).

- **28 days, rolling.** The session and its cookie last 28 days from the person's last use, so staying logged in is renewed while they keep using the app. For a logged-in session the cookie is re-issued with a fresh 28-day expiry at most once an hour, and a session idle for more than 28 days is destroyed. Clearing cookies logs the person out.
- **Own save path.** Session files live in `APP_BASE_DIR/app/private/sessions` (created on demand, mode 0700, git-ignored) and `session.gc_maxlifetime` is set to 28 days, so another site sharing the same PHP install cannot garbage-collect these sessions early.
- Cookie flags: `HttpOnly`, `SameSite=Lax`, `Secure` when the request is HTTPS (decided by `Url::isHttps()`, §16.3 — the same check that builds absolute links).
- Session keys set by the framework: `user_id` (the login), `csrf_token`, the in-flight sign-in state `login_email` / `login_terms`, `invite` (an opened invite link, v3.0.0, §16.11), `google_signin` (`state` and `nonce` while the person is at Google's sign-in page, v3.0.0) and `support` (`user_id` and `tenant_id` of the platform user while they act as a tenant owner, v3.0.0 — see Support access below); `Session` keeps `_last_activity` and `_cookie_refreshed_at`.
- `Session` uses `time()` for cookie and idle arithmetic. This is PHP runtime session mechanics, not a persisted application timestamp, so it is the one sanctioned use outside `Clock` (§10); every timestamp written to the database still comes from `Clock` in a Service.

**AuthMiddleware** on every protected route:
1. Starts the session via `Session::start()`
2. Redirects to `/login?next={current_url}` if `user_id` not in session
3. Loads user via `User::findById()`
4. If route has `{tenant_id}` param, verifies `user.tenant_id === route tenant_id` — returns 403 if mismatch
5. Sets `$request->user` (array)

**TenantMiddleware** resolves before AuthMiddleware in the stack:
1. Reads `{tenant_id}` from route params — redirects to `/logout` if missing
2. Loads tenant via `Tenant::findById()` — returns 404 if not found
3. Sets `$request->tenant` (array)

**One email = one user = one tenant.** `users.email` is globally unique. A person who needs a second tenant uses a different email address.

**Sign-in / sign-up flow** (`AuthController` + `LoginCodeService`; routes in §16.4):
1. `GET /login` — one field: email. `POST /login` requests a code: `LoginCodeService::requestCode()` validates the address, applies the per-IP limit, cancels earlier unused codes for that address, stores the new code hashed (`password_hash()`) in `login_codes`, and emails the plain code via `EmailService::sendLoginCode()`. The controller then always redirects to `/login/verify` (address held in `$_SESSION['login_email']`).
2. `GET/POST /login/verify` — `LoginCodeService::verifyCode()`.
   - A code lasts **15 minutes**.
   - **3 wrong guesses cancel the code** (`login_codes.attempts`, counted atomically before the comparison so parallel requests cannot exceed the cap); the person must request a new one. The old `$_SESSION` lockout counters are gone.
   - A correct code is consumed (`used_at`); it cannot be reused.
   - **Known email:** the user is logged in.
   - **Unknown email:** inside one `Database::transaction()`, `SignupTenantResolver` places the user (framework default: **creates a new tenant and the user becomes its `owner`**, name derived from the email — §16.9) and the user row is inserted, then the person is logged in. There is no "create an account?" step. The platform owner is alerted (`sendPlatformOwnerSignupAlert`).
   - **Terms (only when `signup.require_terms` is on):** an *unknown* email that has verified its code is sent to `GET/POST /login/terms` first; nothing is created until they accept. The "verified, awaiting terms" state is `$_SESSION['login_terms']` and expires after 15 minutes. Existing users never see this step; with the flag off there is no such step.
3. `POST /login/resend` — a new code for the address in the session. It counts toward the limit and cancels earlier unused codes, exactly like step 1. The resend form is its own `<form>`, never nested inside the verify form.
4. **On success** (`AuthController::completeLogin()`): `session_regenerate_id(true)`, `$_SESSION['user_id']` set, `UserService::recordLogin()` writes the UTC login timestamp via Clock (a failure is logged and does not block the person — the code is already spent), redirect to `/tenant/{tenant_id}/dashboard`.
5. **Rate limit:** at most **5 code requests per hour per IP address** (requests and resends together; one `login_codes` row per request). The over-limit response re-renders `/login` with "Too many requests. Please try again later." and no email is sent.
6. **CSRF:** every POST form in this flow carries a hidden `csrf_token` (the partial `Views/partials/csrf-field.php`, which calls `Session::csrfToken()`); the controller checks it with `Session::csrfValid($data)`. A mismatch re-renders the screen with "Invalid request. Please try again." `Session` is the one place the token is made and checked — every framework and template controller uses it (v3.0.0).

**Continue with Google (v3.0.0)** (`AuthController` + `GoogleSignInService`; Google's OpenID Connect server flow, written without outside libraries):

- **Keys are optional.** `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (and `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET`) in `app/.env`, read with `Env::get()` into `$config['oauth']['google']` / `['microsoft']`. The sign-in screen always shows "Continue with Google"; it is enabled only when both its client ID and secret are set (`AuthController::oauthKeysSet()`), otherwise it is shown disabled. The view receives `$googleEnabled` and `$microsoftEnabled`. Keys are per app; the return address `{site}/login/google/callback` must be registered with Google exactly (a production address is added to the same registration). **Continue with Microsoft is not built in v3.0.0 (future enhancement).** Its key stubs and `oauth` entry are in place, but its button is commented out in `auth/login.php`, so setting the `MICROSOFT_*` keys enables nothing.
- `GET /login/google` (`googleStart`): when Google's keys are set, `GoogleSignInService::authorizationRequest()` builds Google's sign-in address (`scope=openid email`, a random `state` and `nonce`); the state and nonce are kept in `$_SESSION['google_signin']` and the person is redirected to Google. Without keys it redirects to `/login`.
- `GET /login/google/callback` (`googleCallback`): the saved state and nonce are removed from the session (one use). A missing or wrong `state`, or an `error` from Google (e.g. the person pressed Cancel), re-renders `/login` with "Invalid request. Please try again." Otherwise `GoogleSignInService::exchangeCode()` posts the code to Google's token endpoint (curl, 10-second limit) and reads the ID token. Because the token comes straight from Google over https, Google says its signature need not be checked; issuer, audience (our client ID), expiry and nonce are checked.
- **Same address = same account, when Google confirms the address** (the product rule). If `email_verified` is not true the sign-in is refused: "Google did not confirm this email address." Google's own guidance is to identify users by its `sub` claim rather than email; FrankPHP keys on the confirmed email address, by the product rule above.
- A confirmed address then goes **exactly the same way as a correct code**: `LoginCodeService::signInConfirmedEmail()` (known address → signed in; unknown → the terms step when `signup.require_terms` is on, otherwise a new tenant + owner via `AccountService`) and `AuthController::continueConfirmedEmail()` → `completeLogin()`. The 5-per-hour code-request limit does not apply (no email is sent).

**Support access (v3.0.0)** (`AuthController` + `UserService`). The product rule: a `platform` user logs in as a tenant owner at will; no record is kept; nothing more.

- `POST /tenant/{tenant_id}/support/start` (`supportStart`, field `target_tenant_id`, CSRF-checked): `UserService::ownerForSupportAccess()` refuses anyone who is not `platform` and a tenant with no owner, and finds the owner with the inherited, tenant-scoped `User::where()`. The platform user's own `user_id` and `tenant_id` are kept in `$_SESSION['support']`, `user_id` becomes the owner's, and the person lands on the owner's dashboard. From then on they are the owner in every respect (`AuthMiddleware` is unchanged: the user really is the owner), including everything the owner may do.
- `POST /tenant/{tenant_id}/support/stop` (`supportStop`, CSRF-checked) — the Release Tenant button: `UserService::platformUserForSupportReturn()` re-reads the kept user with the inherited, tenant-scoped `User::find()` and checks they are still `platform`; `user_id` becomes theirs again and `support` is cleared, landing on their own dashboard. If they are no longer a `platform` user the session is destroyed and they go to `/login`.
- **No record.** Neither step calls `UserService::recordLogin()`, so the owner's (and the platform user's) `accessed_at` is untouched. Nothing is written to the database.
- Every refusal (bad CSRF token, not `platform`, no owner, no support session) redirects to the person's own dashboard with `?error=forbidden` (the §11 convention).
- Every change of signed-in person — each sign-in, support start and stop — goes through one private helper, `AuthController::switchSessionUser()` (new session id, in-flight sign-in keys cleared, `support` set or cleared). Any normal sign-in therefore ends support access.
- `Session::supportAccess()` is true while `support` is set. The template app's layout and top bar call it: the whole top bar turns red (`.topbar--support`, `app-header.css`) and shows a Release Tenant button and an "Acting as Tenant Owner" chip, centred. The Capture Tenant button is on the template's Edit Tenant screen (platform only). These screens are app-owned; the framework supplies the two routes, the two `UserService` operations and `Session::supportAccess()`.

`GET /logout` destroys the session (`Session::destroy()`) and redirects to `/login`. During support access that ends the platform user's session too.

Apps that need a different placement model (e.g. invite into an existing tenant) replace the `SignupTenantResolver` — see §16.9.

**Role checking** is done in controllers, not middleware. Pattern used in `TenantSettingsController`:
```php
if (($user['role'] ?? '') !== 'owner') {
    return Response::redirect('/tenant/{id}/somewhere?error=forbidden');
}
```

`{id}/somewhere` must be a route the forbidden user can actually reach (e.g. `/dashboard`) — never the same gated route the check is running in. Redirecting back to the page that just failed its own check causes an infinite redirect loop on every request from that user (this was a real bug in `TenantSettingsController` — fixed 2026-08-06).

**Convention: forbidden access always redirects to the tenant's home/dashboard route, and that destination must render the `?error=forbidden` flash message.** The redirect alone is not sufficient — the receiving view needs its own `$_GET['error'] === 'forbidden'` check to actually display something, or the user lands on the dashboard with no explanation and it reads as a broken link. `home/dashboard.php` is the reference implementation:

```php
<?php if (($_GET['error'] ?? '') === 'forbidden') : ?>
    <div class="alert alert-danger settings-alert"><i class="bi bi-lock-fill me-2"></i>You don't have permission to view that page.</div>
<?php endif; ?>
```

Any new role-gated controller/view pair must follow both halves of this pattern together, not just the redirect.

## 13. Security Notes

- `.env` file sits outside the public web root (`/public`) — credentials cannot be requested directly by a browser
- All DB queries use PDO prepared statements
- There are no passwords (v3.0.0). Sign-in codes are 6-digit, random (`random_int`), stored only as `password_hash()` hashes, valid 15 minutes, single-use, cancelled after 3 wrong guesses, and requests are limited to 5 per hour per IP (§11)
- Known and unknown email addresses behave identically until a code is verified, so the sign-in screen does not reveal whether an address has an account. The person sees no difference; behind the scenes the platform owner is alerted when an address with no account requests a code
- Sessions: 28-day rolling, `HttpOnly`, `SameSite=Lax`, `Secure` on HTTPS, stored in `app/private/sessions` (§11)
- CSRF: one per-session token, made by `Session::csrfToken()` and checked by `Session::csrfValid()` (`hash_equals`) — no controller has its own copy (v3.0.0)
- Continue with Google (v3.0.0, §11): a random `state` (anti-forgery) and `nonce` (replay) per attempt, used once; the ID token's issuer, audience, expiry and nonce are checked; an address Google has not confirmed (`email_verified`) is refused. Google keys live only in `app/.env` and flow through `$config['oauth']`
- Support access (v3.0.0, §11): only a `platform` user can start it (checked server-side in `UserService`); the owner is found and the platform user re-checked with tenant-scoped inherited finders; both steps are CSRF-checked POSTs that regenerate the session id. By the product rule no record of support access is kept
- `htmlspecialchars()` on all user-supplied output in views
- Tenant isolation enforced at middleware level (route param vs session user) and at model level (tenant_id in all queries)
- The single sanctioned cross-tenant read is the Users dashboard for role `platform` (v2.2.0). It is decided in the template app's `UserManagementService` (app-owned since v3.0.0) from the authenticated user's role, never from request input, and it is still built from tenant-scoped calls to the inherited `User::all()` (v3.0.0; previously `User::allByTenant()`). `owner` stays tenant-scoped. Role `user` is refused by the controller, and the app nav hides the link from it.
- `saveSettings()` methods in both `User` and `Tenant` maintain explicit column allowlists — arbitrary columns cannot be written via settings forms
- Multi-statement PDO mode is disabled after schema import
- SMTP credentials live exclusively in `.env` and flow through `config['mail']` → `EmailService::fromConfig()` → the container singleton. They are never present in any service or controller file.
- Persisted timestamps are stored as UTC `DATETIME` values and generated through `Frank\Core\Clock` in the Service layer; models receive pre-computed UTC strings as parameters and never call Clock directly.
- Terms & Conditions acceptance (v2.1.0, §16.9) is enforced **server-side** in `LoginCodeService::acceptTerms()` when `signup.require_terms` is on, before the tenant and user are created. A view's `required` checkbox or disabled submit button is UX only and can be bypassed — never rely on it.
- Consent columns (`users.terms_accepted_at`, `terms_version`) are public properties on `User` (v3.0.0). `find()` loads them and `save()` writes them back as fetched, so recorded consent only changes if a Service sets them (§16.2).

## 14. What The Framework Deliberately Does Not Include

- No ORM — queries are hand-written SQL via PDO
- No template engine — plain PHP views
- No event system
- No queue system
- No automatic CSRF protection — nothing checks forms for you. The framework supplies the token and the check (`Session::csrfToken()`, `Session::csrfValid()`, partial `Views/partials/csrf-field.php`, v3.0.0); the sign-in forms (§11), the invite accept form (§16.11) and the two settings save actions (`POST …/account/save`, `POST …/tenant-settings/save`) use them. Other application forms must include the partial and call `Session::csrfValid()`
- No general rate-limiting facility — only sign-in code requests are limited, per IP (§11)
- No Composer — zero external dependencies (Google sign-in is written with PHP's own curl and json, v3.0.0)
- No external date/time library — UTC/local handling is provided by `Frank\Core\Clock` using native PHP date/time classes

### 16.6 Framework Future Changes

FrankPHP may add or modify framework-owned tables, models, and routes in future versions (for example, adding OAuth2 or SSO support). When this happens:

- CODEBASE.md Section 16 will be updated to reflect the new schema
- `schema.core.sql` is updated for fresh installs, and an idempotent, hand-run script ships in `sql/migrations/` for existing installs, with notes in `Versions/` (both in the release zip)
- MYAPP.md will not be affected unless the application has deviated from framework defaults (which should already be recorded in the MYAPP.md Known Deviations section)

**Worked example — v2.1.0.** Signup terms acceptance added `terms_accepted_at` / `terms_version` to `users` (and to `signup_tokens`, which v3.0.0 later dropped). Shipped as: `schema.core.sql` (fresh installs), `sql/migrations/v2.1.0_signup_terms.sql` (existing installs — each `ALTER` guarded by an `information_schema` check, safe to re-run), `Versions/FrankPHP_v2.1.0_migration_notes.md`. The code stays safe on an un-migrated install (columns written only when the opt-in feature is on) and the feature fails fast with a clear message if enabled before the migration runs. There is no migration runner yet — a structured migration/upgrade tool is on the ROADMAP.

**Worked example — v3.0.0 (breaking).** Passwordless sign-in shipped as `schema.core.sql` (fresh installs: no seed rows, no `password_hash`, unique `users.email`, `login_codes`, no token tables) and `sql/migrations/v3.0.0_passwordless.sql` (existing installs, hand-run, idempotent). Order matters: the unique key on `users.email` is added **first** and the script stops there if one address exists in two tenants (the file's header gives the `SELECT` that lists them); only then are `login_codes` created and `password_hash`, `password_reset_tokens` and `signup_tokens` dropped. Unlike v2.1.0 the code is **not** safe on an un-migrated database — run the script when deploying v3.0.0.

This separation is what makes framework upgrades safe — application-layer documentation and framework-layer documentation do not overlap.

### 16.7 Extending Framework-Owned Tables (Tenants and Users)

Almost every application built on FrankPHP needs to store more about a tenant or a user than the framework's own `tenants`/`users` tables hold. The framework's `tenant` and `user` concepts are deliberately generic — a "tenant" might represent a venue, a coaching business, an agency client, or anything else, and a "user" might need domain-specific data (profile fields, preferences, measurements, anything) that has nothing to do with authentication.

**The rule: extend by composition, never by modification.**

- Do not add columns to `tenants` or `users`.
- Do not edit `Models/Tenant.php` or `Models/User.php`.
- Do not edit any framework-owned Service to add application-specific fields or logic.

Any of the above is technically possible but explicitly unsupported: the next time `framework/` is replaced by a newer release, those edits are silently gone. There is no merge step — a framework update is a folder replacement.

This rule is addressed to **applications**. Columns the framework itself adds in a release (e.g. v2.1.0's `terms_accepted_at` / `terms_version`) are framework changes shipped with a migration (§16.6), not app extensions — they don't contradict the rule.

**The supported pattern: a satellite table with a foreign key.**

The application defines its own table for the extra data, with a foreign key back to `tenants.id` or `users.id`, plus an application-owned Model and (if there's business logic beyond simple CRUD) an application-owned Service. The core `tenants`/`users` tables and framework Models never change. Two worked examples:

1. **A booking platform where a "tenant" is a venue.** The application adds a `venue_details` table (address, capacity, amenities…) with a `tenant_id` foreign key, plus `App\Models\VenueDetails`. The core `Tenant` row is still just "a tenant" as far as the framework is concerned — "venue" is an application-layer concept layered on top via the join.
2. **A coaching platform where a "user" is a client with fitness data.** The application adds a `client_profiles` table (bodyweight, progress photos…) with a `user_id` foreign key, plus `App\Models\ClientProfile`. `Services/UserService.php` (framework-owned) is untouched; an application-owned service composes `User` + `ClientProfile` data where needed.

Presentation for both is already application-owned — `Views/` lives entirely in `app/`, so a dashboard can freely display core tenant/user fields alongside satellite-table fields side by side.

**Wiring the application's own schema:**

`app/bootstrap.php` may run its own schema file the same way `framework/bootstrap.php` runs `schema.core.sql` — using the same `Database::runSchemaFileIfMissingTable()` primitive (see §9), guarded by `file_exists()` so a project with no application-specific tables yet is completely unaffected:

```php
// App-owned schema — for tables that extend the framework's Tenants/Users
// with application-specific data (see CODEBASE.md §16.7). No-op until
// app/sql/schema.app.sql actually exists. Once you add one, change the
// sentinel table name below to a real table it creates.
$appSchemaPath = APP_BASE_DIR . '/app/sql/schema.app.sql';
if (file_exists($appSchemaPath)) {
    \Frank\Core\Database::runSchemaFileIfMissingTable($appSchemaPath, 'CHANGE_ME_sentinel_table');
}
```

`app/sql/schema.app.sql` does not ship by default — most new installs don't need one yet. Create it (and update the sentinel table name above to match) only once the application actually has its own tables to create on first boot.

### 16.8 Overriding Framework Email Templates

Three email flows are framework-owned because a framework-owned Service triggers them directly (`LoginCodeService`, `InviteService`, `AccountService` — see §16.5): the sign-in code, the invite (v3.0.0) and the platform-owner signup alert. Every application needs these to work, but the wording and branding inside them is exactly the kind of thing a real business wants in its own voice — this is a deliberate, narrow exception to "don't touch framework-owned files."

**The rule:** never edit `Services/Email/Templates/*.php` directly. Override the template *class* via config instead.

`config('mail.templates')` (set in `app/Config/config.php`, part of the `mail` array) is an optional map from a flow key to a replacement class name. `EmailService` checks this map first and falls back to its own default when a key isn't set — so a fresh install with an empty map behaves exactly as before, no setup required:

```php
'mail' => [
    // ...existing keys...
    'templates' => [
        // 'login_code'                  => \App\Email\Templates\MyLoginCodeTemplate::class,
        // 'invite'                      => \App\Email\Templates\MyInviteTemplate::class,
        // 'platform_owner_signup_alert'  => \App\Email\Templates\MyPlatformOwnerAlertTemplate::class,
    ],
],
```

An override class must implement the same static methods, with the same arguments, as the framework default it replaces — checked by convention, not by an interface (same pattern as the router's shorthand handler strings):

| Flow key | Required static signature |
|----------|---------------------------|
| `login_code` | `buildHtml(string $email, string $code, int $expiry): string` and `buildText(string $email, string $code, int $expiry): string` — the email carries the code only, never a link |
| `invite` | `buildHtml(string $email, string $inviteUrl, int $expiryDays): string` and `buildText(string $email, string $inviteUrl, int $expiryDays): string` — *v3.0.0*; one template for both kinds of invite |
| `platform_owner_signup_alert` | `buildHtml(string $email, string $event): string` and `buildText(string $email, string $event): string` |

The override class can live anywhere under `App\`; it does not need to sit in any particular folder.

**Vendored PHPMailer:** `Services/Email/PHPMailer/` is a vendored copy (no Composer), currently version 6.4.1. Because nothing watches it automatically, checking the upstream repo (github.com/PHPMailer/PHPMailer) for security releases is a manual step that should happen as part of cutting each framework release, not something either the framework or an application does at runtime.

### 16.9 New Accounts: Tenant Creation and Terms Acceptance (v2.1.0, reworked v3.0.0)

Since v3.0.0 there is no separate sign-up. A new account is created when an email address that has no user yet verifies its emailed sign-in code (§11).

#### Tenant-on-first-sign-in

An unknown email that verifies its code creates a **new tenant** and the person becomes its **`owner`** (before v2.1.0: tenant 1, role `user`). One email = one user = one tenant.

- **Tenant name** — derived from the email by `TenantNameGenerator`, no extra form field: business domain → organisation name (`jane@acme-corp.com` → "Acme Corp"); free-mail domain (gmail, outlook, icloud…) → "Jane's Workspace". The owner can rename it in Tenant Settings. The user's display name is derived from the email local part (`john.doe@…` → "John Doe").
- **Slug** — from the name, made unique by `TenantService::create()` (`acme-corp`, `acme-corp-2`, …).
- **`company_email`** — set to the email.
- **Atomic** — tenant insert and user insert run in one `Database::transaction()` inside `AccountService::create()` (v3.0.0; invites use the same method). Any failure rolls back both and the person sees "Account creation failed". The code is already spent at that point, so they request a new one.
- Two people from the same company signing in separately get **two tenants** — joining an existing tenant is done by an owner's invite (v3.0.0, §16.11).
- There is no seeded tenant or user: a fresh install starts empty and the first person to sign in creates the first tenant.

**Changing the policy** — replace the `SignupTenantResolver` binding in `app/bootstrap.php`:

```php
// Example: every new person joins tenant 1 as 'user' (the pre-2.1 behaviour)
$container->override(\Frank\Services\SignupTenantResolver::class, fn ($c) =>
    new class implements \Frank\Services\SignupTenantResolver {
        public function resolve(string $email, string $name): array {
            return ['tenant_id' => 1, 'role' => 'user'];
        }
    }
);
```

`resolve()` runs inside the account-creation transaction — any rows it writes roll back with the rest.

#### Terms & Conditions acceptance (opt-in)

When enabled, the framework enforces acceptance **server-side** and records **when** and **which version**. Off by default — an app that upgrades without touching config shows no terms step.

**Config** (`app/Config/config.php` — a literal, not `.env`):

```php
'signup' => [
    'require_terms' => true,       // missing / false = feature off
    'terms_version' => '2026-10',  // optional; stored with each acceptance
],
```

**Where it appears (v3.0.0):** only an **unknown** email that has just verified its code is sent to `GET /login/terms`, **before** the tenant and user are created. Existing users are never shown it. When the flag is off there is no terms step and nothing is recorded. The "verified, awaiting terms" state is held in `$_SESSION['login_terms']` and expires after 15 minutes (`LoginCodeService::isTermsStepOpen()`); after that the person starts again from `/login`.

**Protocol contract (for app-owned views):**

- `POST /login/terms` must post a field named `terms_accepted` with value `1`, plus the `csrf_token` (include `Views/partials/csrf-field.php`).
- Render `$error` (shown on rejection: "You must accept the Terms & Conditions to continue.") and `$email`.
- A `required` attribute / disabled submit button is UX only — the server check is the enforcement.

**Behaviour matrix:**

| `require_terms` | Email | Result |
|---|---|---|
| off / missing | known or unknown | No terms step; **nothing recorded** (terms columns stay NULL and are not written) |
| on | known | Logged in; no terms step |
| on | unknown, `terms_accepted=1` not posted | Terms screen again with an error; no tenant, no user |
| on | unknown, `terms_accepted=1` posted | Tenant + owner created; acceptance recorded; logged in |

**What is recorded:** `terms_accepted_at` = the UTC moment the terms step was accepted (`Clock::nowUtcString()`, same value as the user's `created_at`), and `terms_version`, written straight onto the new `users` row. Users created before v2.1.0 or with the feature off stay NULL — never backfill. Age confirmation or any other statement in the checkbox label is covered by the same timestamp; there is no separate column.

**Reading consent:** the columns come back from `User::findById()` / `findByEmail()` (`SELECT *`). They are also public properties on `User` (v3.0.0), so `User::find()` and `where()` return them. A dedicated read accessor is on the ROADMAP.

**Migration requirement:** existing installs must run `framework/sql/migrations/v2.1.0_signup_terms.sql` (idempotent) **before** enabling `require_terms`. If the flag is on and the `users` columns are missing, the first use of `LoginCodeService` throws a `LogicException` naming the script. Order: deploy code → run migrations → enable flag.

**Starter app reference implementation:** `app/Views/auth/login-terms.php` (checkbox, disabled-until-ticked button), `app/Views/auth/terms.php` + `App\Controllers\LegalController` + `GET /terms` in `app/bootstrap.php` (placeholder — **replace the content before going live**; the route is app-owned because upgraded apps don't receive new starter views).

**Not yet included (future work):** re-acceptance when `terms_version` changes (e.g. a login-time gate), a consent audit log / IP + user-agent on `users`, config-driven terms URLs.

### 16.10 User and Tenant Operations (v3.0.0)

**The principle.** The framework owns the `User` and `Tenant` models and supplies *operations* on them. The app owns every screen, the friction, the warnings and the housekeeping of its own data. The framework never adds controls to app screens and never deletes anything on its own initiative. There are no framework routes, controllers or views for deleting a user, changing a role or deleting a tenant; how an app uses the operations is the app developer's decision.

**What the framework enforces, inside the operations, for every app:**

| Operation | Refuses when | Failure type (`$result->errorType`) |
|---|---|---|
| `UserService::deleteUser(int $tenantId, int $targetUserId): ServiceResult` | the target does not exist in that tenant (another tenant's id counts as not existing) | `not_found` |
| | the target's role is `owner` — an owner's account is only ever removed by deleting the whole tenant | `owner_requires_tenant_delete` |
| `UserService::changeRole(int $tenantId, int $targetUserId, string $newRole): ServiceResult` | the target does not exist in that tenant | `not_found` |
| | the target's current role is `owner` or `platform` | `role_protected` |
| | `$newRole` is `owner` or `platform` | `role_not_assignable` |
| | `$newRole` is empty or longer than 50 characters (the column size) | `validation` |
| `TenantService::deleteTenant(array $actingUser, int $tenantId): ServiceResult` | the acting user is neither the owner of that tenant (`role` `owner` and the same `tenant_id`) nor a `platform` user | `forbidden` |
| | the tenant does not exist | `not_found` |
| `UserService::saveSettings(userId, tenantId, data): bool` | `name` is present but not a string, empty after trimming, or longer than 255 characters — the whole save fails and nothing is written | returns `false` |

- `changeRole()` trims `$newRole` and compares `owner` / `platform` case-insensitively, so `" Owner"` cannot slip through. It does **not** check the role against a list: which roles exist is the app's business. The roles `owner` and `platform` are only ever set or removed by hand in the database.
- `deleteUser()` and `changeRole()` use the methods `User` inherits from `BaseModel`: `User::find(id, tenantId)` to load the user (tenant-scoped), then `delete()` or, after setting `role` and `updated_at` (`Clock::nowUtcString()`), `save()`. The `User` model has no delete or role functions of its own.
- `TenantService::deleteTenant()` deletes the tenant row; the foreign key `fk_users_tenant ... ON DELETE CASCADE` removes every user in it. No separate user deletes are made.
- `saveSettings()` accepts `name` (trimmed) and `timezone`. Timezone behaviour is unchanged (empty string becomes NULL). `email` is not writable: a person cannot change their email, and nobody changes another person's name.
- Both services take the *tenant id explicitly* and every model query is tenant-scoped, so using one tenant's id with another tenant's user is refused, never executed.

**What the framework does NOT decide (the app's job):** who may call an operation (owner deleting users, "delete my own account", who may change roles), confirmation and warning screens, what happens to the app's own data that references a deleted user or tenant, ending the session after a self-delete, and where to redirect. `Frank\Core\Session::destroy()` is available for the session part.

**The template app's example (app-owned, not framework behaviour).** `app/Controllers/UserAdminController.php`, bound and routed in `app/bootstrap.php` with `[$tm, $auth, $json]`, is one worked example. A developer may change or delete it.

| Method | Pattern | Action | Example's rule |
|---|---|---|---|
| POST | /tenant/{tenant_id}/users/invite | `sendInvite` | owner (sends `join_tenant`) or platform (sends `new_tenant`); field `email`; `InviteService::createInvite()`; result shown in the Users screen banner (§16.11) |
| POST | /tenant/{tenant_id}/account/delete | `deleteMyAccount` | role `user` only (User Settings shows it to no other role) |
| GET | /tenant/{tenant_id}/tenant-delete | `showTenantDelete` | the warning screen, owner only |
| POST | /tenant/{tenant_id}/tenant-delete | `deleteTenant` | owner only; the typed `tenant_name` must equal the tenant's name exactly (server-side check) |
| GET | /tenant/{tenant_id}/users/edit | `showUserEdit` | platform (any tenant, `user_tenant_id` from the row) or owner (own tenant); query `user_id`, `user_tenant_id` |
| POST | /tenant/{tenant_id}/users/save | `saveUser` | as above; saves the name only, via `UserService::saveSettings()` |
| POST | /tenant/{tenant_id}/users/delete | `deleteUser` | as above; `UserService::deleteUser()` (the owner is refused by the service) |
| GET | /tenant/{tenant_id}/tenants/edit | `showTenantEdit` | platform only; query `edit_tenant_id`. The screen's Capture Tenant button posts to the framework's support access route (§11) |
| POST | /tenant/{tenant_id}/tenants/save | `saveTenant` | platform only; `TenantService::saveSettings()` |
| POST | /tenant/{tenant_id}/tenants/delete | `deleteTenantAsPlatform` | platform only; the typed `tenant_name` must equal the tenant's name exactly, then `TenantService::deleteTenant()` |

The example's friction: deleting your own account, or another user from Edit User, is one confirmation ("Are you sure? This cannot be undone"); a platform user deleting a tenant from Edit Tenant must type its name exactly (same server-side check); the owner deleting their own tenant gets a warning screen (the tenant and every user in it are lost, cannot be undone) and the final button only works once the tenant's name is typed exactly. After deleting your own account or the tenant the example calls `Session::destroy()` and redirects to `/login`. Every POST form on these screens, including the settings save forms, carries the `csrf_token` (partial `Views/partials/csrf-field.php`, checked with `Session::csrfValid()`, the same mechanism as the login forms). The example views are `settings/account-settings.php` (User Settings: editable name, Delete my account for role `user`), `settings/tenant-settings.php` (Tenant Settings: owner-only Delete tenant entry), `settings/tenant-delete.php`, `users/management-dashboard.php` (Your details card; an edit icon on every other row — owner rows open Edit Tenant, the rest Edit User), `users/user-edit.php` and `users/tenant-edit.php`.

### 16.11 Invites (v3.0.0)

**What they are.** An invite brings a new person in by email, with no code to type. The framework supplies the operations (`InviteService`), the link and welcome screen (`AuthController`), and the email. Who may send which kind is the app's decision.

| Kind | Typically sent by (template app) | The invited person gets |
|---|---|---|
| `join_tenant` (`InviteService::KIND_JOIN_TENANT`) | an `owner` | a user in the **sender's** tenant, role `user` (`JoinTenantAsUser`) |
| `new_tenant` (`InviteService::KIND_NEW_TENANT`) | a `platform` user | a **new** tenant of their own, role `owner` (`CreateTenantForSignup`, the default sign-up placement — not the app's resolver) |

Sign-up from `/login` is unchanged: a new tenant and owner.

**Rules the framework enforces (`InviteService`):**

- Refused if the address already has an account (`account_exists`, via `User::findByEmail()` — `users.email` is unique across the platform).
- Refused if the address already has a live (not expired) invite **from the sender's tenant** (`invite_open`). Expired invites do not block. Two different tenants may each invite the same address; whichever link is used first creates the account, and the other link is then refused because the address has an account.
- An invite lasts 7 days, works once and cannot be cancelled.
- The invite is saved and the email sent in one transaction: if the email cannot be sent, nothing is saved (`email_failed`) and the sender can try again at once.
- The token is 32 random bytes; only its SHA-256 hash is stored, and the token is never returned to the caller — it exists only in the email.

**The link: `GET /invite/{tenant_id}/{token}`.** No code is needed: the link went only to the invited address, so opening it proves the address. `findOpenInvite()` looks the token's hash up with the inherited `where()` **within the tenant in the link**. Missing, used or expired → the expired screen (`auth/invite-expired`). Otherwise the invite is remembered in `$_SESSION['invite']` (`tenant_id`, `invite_id`, `email`) and the welcome screen opens (`auth/invite-welcome`). The address cannot be changed; someone who wants a different address uses the normal sign-up.

**Nothing is created when the link is opened.** Company mail systems open links to scan them; they never press buttons. The account is created only when the person presses the welcome screen's button.

**Accepting: `POST /invite/accept`.** Checks `csrf_token`. `acceptInvite()` re-reads the invite with the inherited `find()`; when `signup.require_terms` is on, `terms_accepted=1` must be posted (the welcome screen shows the same checkbox as sign-up). Then `AccountService::create()` creates the account by kind and **deletes the invite in the same transaction** — if the account fails, the invite stays. Two people pressing the button at once cannot both succeed: the unique key on `users.email` fails the second insert, which rolls back. On success the person is signed in (`completeLogin()`) and lands on their dashboard.

| Outcome | Screen |
|---|---|
| `invite_unusable` (used or expired meanwhile) | expired screen |
| `account_exists` (the address got an account meanwhile) | login screen, address filled in, "That email address already has an account. Please sign in." — the invite stays |
| `terms_required`, `system` | welcome screen again with the error |
| success | signed in, own dashboard |

**Protocol contract (for app-owned views):** `auth/invite-welcome` receives `$email`, `$requireTerms`, optional `$error`, and must post `csrf_token` (include `Views/partials/csrf-field.php`) (and `terms_accepted=1` when `$requireTerms`) to `/invite/accept`. `auth/invite-expired` receives nothing.

**Not included:** cleaning up expired invites, cancelling an invite, a list of sent invites, and a record of who invited whom after acceptance (the invite row is deleted). If someone already signed in opens an invite for a different address and presses the button, they are signed in as the new account.

**Template app (app-owned):** the Invite button on the Users screen's Total Users card opens a modal (`users/management-dashboard.php`) posting to `UserAdminController@sendInvite` (§16.10); results use the screen's standard banner (`?success=invited`, `?error=invalid_email|account_exists|invite_open|invite_email_failed|invite_failed|invalid_request`). Views `auth/invite-welcome.php` (button "Let me see") and `auth/invite-expired.php`.
